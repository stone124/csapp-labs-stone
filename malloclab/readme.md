## 2 认识初始代码

初始版本中，`mm_init` 和 `mm_free` 基本为空。`mm_malloc` 每次调用 `mem_sbrk` 增加堆空间，`mm_realloc` 则申请新块并复制数据。因为释放的空间不会被复用，完整测试中会出现模拟堆耗尽的问题。

一开始让我困惑的是这个宏：

```c
#define SIZE_T_SIZE (ALIGN(sizeof(size_t)))
```

先拆开看里面的 `ALIGN`：

```c
/* 向上取整到 ALIGNMENT 的整数倍 */
#define ALIGN(size) (((size) + (ALIGNMENT - 1)) & ~0x7)
```

这里 `ALIGNMENT` 是 8。我先把它理解成：将字节数向上取整到最近的 8 的倍数，结果满足 `结果 % 8 == 0`，而且不小于原值。例如 12 变成 16，16 保持不变。先理解它的用途，再回头看位运算：加 7 后清除低三位，就实现了这个向上取整。

因此，`SIZE_T_SIZE` 是把 **`sizeof(size_t)` 得到的字节数**向上对齐，用于原始分配器的头部预留空间。例如 `size_t` 占 4 字节时，也会预留 8 字节。后面采用教材的 4 字节 header/footer 布局，就不再依靠这个宏定位头尾；目前代码仍保留着定义。

## 3 实现思路

根据教材，我选择实现一个带头尾的堆。教材中有大量宏定义，读起来能明白意思，但背着写对我有一定难度，所以采用逐个函数实现的方式：先看一个函数大致分为几步，再逐步完成，并在各步中补上需要的宏。

当前采用的是**隐式空闲链表 + 首次适配 + 边界标记合并**。所有块按地址连续排列，依靠块大小找到下一块，没有额外保存空闲块的链表指针。查找时会经过已分配块和空闲块。

### 3.1 先确定块布局，再推导操作宏

普通块布局如下，已分配块和空闲块都保留头尾：

```text
[header：4 字节][payload 与可能的填充][footer：4 字节]
                ↑ bp
```

- header 和 footer 保存相同的“块总大小 + 分配状态”。总大小包含头尾，不等于用户请求的字节数。
- payload 地址按 8 字节对齐，块总大小也是 8 的倍数，普通块最小为 16 字节。
- 总大小的低三位原本都是 0，因此最低位可存状态：1 为已分配，0 为空闲。
- `PACK` 打包大小和状态；`GET_SIZE` 清除低三位得到大小；`GET_ALLOC` 读取最低位。
- `PUT`、`GET` 通过 `uint32_t` 写入和读取一个 4 字节的字。

地址计算统一以 payload 指针 `bp` 为起点，转为 `char *` 后按字节移动：

| 操作 | 计算方式 |
| --- | --- |
| 当前块 header | `bp - W_SIZE` |
| 当前块 footer | `bp + 当前块总大小 - D_SIZE` |
| 下一块 payload | `bp + 当前块总大小` |
| 上一块 footer | `bp - D_SIZE` |
| 上一块 payload | 从上一块 footer 读出大小，再用 `bp` 减去该大小 |

### 3.2 初始化：mm_init

先完成 init，主要分为三步：申请 4 个字（共 16 字节）、设置边界块、调用 `extend_heap` 扩展默认的 4 KiB 堆空间。

| 初始位置 | 用途 |
| --- | --- |
| word[0] | 对齐填充 |
| word[1] | 序言块 header |
| word[2] | 序言块 footer |
| word[3] | 结尾块 header |

`heap_lisp` 先接收堆起始地址，再向后移动 `2 * W_SIZE`（8 字节），指向序言块 footer，作为遍历堆的起点。这里操作的是堆，不是栈。

初始化并扩展堆后，整体布局是：

```text
[填充 4B][序言 header 4B][序言 footer 4B][普通块……][结尾 header 4B]
                         ↑ heap_lisp
```

序言块总大小为 8，标记为已分配，没有实际 payload。结尾块只有 header，以“大小为 0、已分配”标记堆结束。边界块让普通块的遍历和前后合并可以统一处理。

### 3.3 扩展堆：extend_heap

参数 `words` 的单位是字，每字 4 字节。先换算为字节，再用 `ALIGN` 向上对齐，随后调用 `mem_sbrk`。

`mem_sbrk` 成功时返回新增区域的起点，用作新空闲块的 payload 指针。它前面的旧结尾 header 被改成新空闲块的 header，再设置 footer 和新的结尾 header。最后调用 `coalesce`，与前面的空闲块合并，返回合并后的 payload 指针。

`mem_sbrk` 失败返回 `(void *)-1`；`extend_heap` 将它转换为自己的失败结果 `NULL`。模拟堆只能扩展，释放块后不会缩小。

### 3.4 分配：mm_malloc → findfit → place

1. 用户请求 0 字节时返回 `NULL`。
2. 将请求换算为包含头尾的块总大小：最小为 16 字节，否则是 `ALIGN(size) + D_SIZE`。
3. `findfit` 从 `heap_lisp` 开始向后遍历，返回第一个足够大的空闲块，遇到大小为 0 的结尾块停止。
4. 找到后调用 `place`：剩余大小至少为 16 字节时拆成“已分配块 + 空闲块”，否则把整个块分配出去。
5. 没找到时，扩展 `MAX(CHUNK_SIZE, 块总大小)` 字节，再执行 `place`。

例如，一个 64 字节的空闲块用于满足 16 字节的用户请求，实际分配块大小为 24 字节：

```text
拆分前：[                  64 字节空闲块                  ]
拆分后：[24 字节已分配块][          40 字节空闲块          ]
```

`place` 只更新元数据，不清零 payload。

### 3.5 释放与合并：mm_free → coalesce

`mm_free` 将块头尾的分配位都改为 0，再立即尝试合并相邻空闲块。

| 前块状态 | 后块状态 | 合并方式与返回值 |
| --- | --- | --- |
| 已分配 | 已分配 | 不合并，返回当前 bp |
| 空闲 | 已分配 | 与前块合并，返回前块 bp |
| 已分配 | 空闲 | 与后块合并，返回当前 bp |
| 空闲 | 空闲 | 三块合并，返回前块 bp |

只更新合并后最外侧的 header 和 footer。先写入新 header，再通过 `FTRP` 计算新 footer 的位置；中间旧的头尾不再作为块边界使用。

### 3.6 调整大小：mm_realloc

按以下顺序处理：

1. `ptr == NULL`：等价于 `mm_malloc(size)`。
2. `size == 0`：释放旧块并返回 `NULL`。
3. 原块足够大：保留原地址，必要时拆分，并将剩余空闲块与后块合并。
4. 相邻空闲空间足够：把已分配邻块的可用大小计为 0，空闲邻块计入容量；将当前块标为空闲并调用 `coalesce`，然后重新分配。当前实现会合并所有相邻空闲块，即使只向后合并就已足够。
5. 相邻空间不够：先查找其他空闲块，再考虑扩堆。新块分配成功后复制数据，最后释放旧块。

复制字节数取 `min(size, 旧块总大小 - D_SIZE)`，即不超过新请求大小，也不超过旧 payload 容量。当前没有单独记录旧请求大小，旧 payload 容量可能包含对齐填充。

- 原地址不变时不复制。
- 向前合并可能让源和目标重叠，使用 `memmove`，并在 `place` 拆分之前搬运，避免新头尾覆盖旧数据。
- 独立新块与旧块不重叠，使用 `memcpy`；复制完成后调用 `mm_free`。
- 新块申请失败时返回 `NULL`，旧块和数据保持有效。

## 4 测试与当前结果

运行命令：

```bash
make
./mdriver -v -f short1-bal.rep
./mdriver -v -f short2-bal.rep
./mdriver -v -t ./traces/
```

根据本次手动运行结果，两个 short 测试和全部 11 个完整 trace 的 `valid` 均为 `yes`。完整测试共 112372 次操作，平均空间利用率为 77%，吞吐量为 316 Kops，性能得分为 67/100（空间 46 分、吞吐量 21 分）。这些数值来自本次运行，吞吐量会随机器和运行环境变化。

当前主要耗时集中在 trace 7、8，对应 `binary-bal.rep`、`binary2-bal.rep`，分别约为 160、100 Kops。隐式链表首次适配需要反复从头扫描，块多时查找成本较高，后续可以比较显式空闲链表或分离空闲链表。通过现有 trace 表示覆盖到的场景正确，不代表所有边界情况都已验证。

## 5 待完善的边界处理

当前代码仍有需要整理的地方：`mm_init` 的 `mem_sbrk` 失败判断应比较 `(void *)-1`，初始结尾 header 应使用 `PACK(0, 1)`（目前随后会被 `extend_heap` 覆盖）。`mm_free` 尚未处理 `NULL`，大小计算也尚未增加整数溢出和超大请求的检查。
